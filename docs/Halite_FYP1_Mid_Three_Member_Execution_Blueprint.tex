\chapter{Mission, Scope and Acceptance Gate}
\section{What the Team Must Show}
The deliverable is \textbf{one working vertical slice}, not three disconnected demos. A technician chooses a real maintenance asset; inspects dated records; enters a symptom; receives a graph-grounded, evidence-linked diagnostic investigation response; can open source evidence; and sees at least one real historical correction or conflict example. The same commit must have test evidence and a meaningful GitHub CI workflow.

\section{Mandatory Product Workflow}
\begin{enumerate}
\item Load Halite's maintenance-only UI; identify the demo dataset and runtime mode.
\item Open Assets; choose a known asset from the \emph{actual loaded corpus}.
\item Inspect its dated ServiceRecord timeline and original record identifiers.
\item Open Diagnostics with the selected asset; enter a descriptive symptom.
\item Send a real POST request to the existing diagnosis endpoint; show loading, error and success states.
\item Show ranked investigative checks, supporting record identifiers, explanation and citation-validation status.
\item Open at least one cited record in the real source/history interface.
\item Open a real conflict/review example and explain whether it is an allegation, a correction, or an adjudicated relationship.
\item Show GitHub PR/branch evidence and automatic tests; demonstrate healthy running services.
\item Demonstrate a failure case (unknown asset, no data, missing live LLM, or model rate limit) without misleading generated output.
\end{enumerate}

\section{Non-Goals for Mid-I}
\begin{itemize}
\item No new PostgreSQL/SaaS multi-tenancy migration at this stage unless already implemented.
\item No complete Technician Academy, predictive maintenance model, inventory forecasting, or large-scale model training.
\item No full UI redesign that delays integration or changes existing API contracts without agreement.
\item No reimplementation of a functioning conflict engine simply to use a different library.
\item No silent switch to in-memory demo data or hardcoded AI output when claiming real-data functionality.
\end{itemize}

\file{backend/main.py} can fall back to an in-memory graph, and \file{/api/health} reports \file{graph_mode}, \file{using_memory_graph}, \file{maintenance_corpus_loaded}, \file{maintenance_record_count}, and model availability. \textbf{A healthy HTTP status does not establish a healthy real maintenance demonstration.} The gate requires the right runtime mode, corpus presence and functioning record queries.

The current diagnostic route normally raises HTTP 503 when the live model is not available and there is no applicable cached result. The team must demonstrate or disclose this dependency, preserve controlled failure behavior, and avoid presenting mock text as a live diagnosis.

\section{Error Response Agreement}
\begin{itemize}
\item \textbf{400/422}: missing or invalid input; UI shows validation message.
\item \textbf{404}: asset/record absent; UI offers asset reselection.
\item \textbf{503}: model/database required for that operation unavailable; UI does \emph{not} substitute a made-up diagnosis.
\item \textbf{429/5xx}: external rate limit/backend failure; UI displays controlled retry information.
\item \textbf{200 with empty evidence}: do not imply conclusive diagnosis; show insufficient-evidence state.
\end{itemize}
These are desired error-display behaviors. Usman and Umar should keep existing HTTP behavior unless a shared contract change is approved and regression tested.
